# Slack AI Gatekeeper — use case в рамках Dex PKM

**Контекст:** продакт тонет во входящих в Slack (~5/час): вопросы, уточнения, FYI. Хочет батчить разбор (обед + вечер), но каждый раз нужно восстанавливать контекст и решать, что делать. Нужен «гейткипер на входе»: отсечь часть сообщений и/или структурировать + предлагать ответы в своём стиле.

Ниже — как это обработать в рамках Personal Knowledge Management System (Dex), без упора на процессы и митинги.

---

## Что в Dex уже есть и переиспользуем

- **Контекст по людям:** Person pages (`05-Areas/People/`) — роль, компания, Working Style Notes, последние встречи, открытые action items. Хуки при чтении подтягивают `<person_context>`.
- **Контекст по компаниям/проектам:** Companies, Projects, pillars, Week Priorities — как в `/triage` и `/email-process`.
- **Паттерн «входящие → классификация → действия»:** `/email-process`: письма → категории → задачи (Work MCP), mark read/archive, привязка к персонам. Automation rule: делать самому, не давать списки «сделай вручную».
- **Slack MCP (опционально):** официальный `https://mcp.slack.com/mcp` — список чатов, история каналов/тредов, поиск, при необходимости отправка. Подключение: `.claude/reference/notion-confluence-slack-mcp-setup.md`.

Идея: сделать для Slack аналог email-process, но с фокусом на **триаж + черновики ответов**, с контекстом из vault.

---

## Цели в терминах PKM

1. **Единый контекст:** сообщения в Slack обогащаются тем, что уже лежит в Dex (персоны, проекты, недельные приоритеты, открытые задачи).
2. **Батч вместо реактивного режима:** один запуск (например «за последние 4 часа» или «все непрочитанные») → один отчёт с действиями и черновиками.
3. **«Отвечать как я»:** черновики ответов опираются на стиль из `System/user-profile.yaml` (communication) и на «Working Style Notes» в person page отправителя.
4. **Минимум рутины:** не «вот 20 ссылок, разбери сам», а «вот разбор + предложенные ответы; подтверди/правь/отправь».

## Архитектура в рамках Dex

### Вход

- **Источник:** Slack MCP (после добавления в `.cursor/mcp.json.source` и OAuth).
- **Объём:** за период (например «с 9:00 до 13:00») или непрочитанные в выбранных каналах/DM — по аналогии с `after:YYYY/MM/DD` в email-process.

### Контекст из vault (как в email-process + triage)

- **Неделя и приоритеты:** `02-Week_Priorities/Week_Priorities.md` — что сейчас в фокусе.
- **Pillars:** `System/pillars.yaml` — для категоризации и приоритета задач.
- **Персоны:** по автору сообщения искать в `05-Areas/People/Internal/` и `External/`, брать:
  - Role, company, relationship
  - Working Style Notes (как они любят общаться)
  - Last interaction, open action items
- **Проекты/компании:** по каналу или по ключевым словам в сообщении — привязка к `04-Projects/`, `05-Areas/Companies/`.
- **Открытые задачи:** из `03-Tasks/Tasks.md` или Work MCP — для связи «этот вопрос уже есть в задаче» или «стоит создать задачу».

### Обработка (логика скилла)

Для каждого сообщения (или треда):

1. **Классификация:** FYI / вопрос / запрос решения / уточнение / шум / уже закрыто (есть задача или ответ в треде).
2. **Рекомендуемое действие:** ignore | ack_only | needs_reply | create_task | defer (разобрать позже).
3. **Если needs_reply:** черновик ответа:
   - входы: текст сообщения, person context (Working Style, relationship), проект при наличии;
   - стиль: коротко, по делу, без «AI-словаря» (как в `.claude/reference/ai-writing-signs-banned.md`);
   - опционально: 1–2 варианта («короткий ack» / «развёрнутый ответ»).
4. **Если create_task:** те же правила, что в email-process (pillar, priority, context, people), создание через Work MCP.

### Выход (MVP)

- **Отчёт в Markdown** (например `00-Inbox/Slack/digest-YYYY-MM-DD-HH.md` или в чат):
  - по каждому сообщению/треду: автор, канал/DM, дата, суть, **рекомендация** (ignore/ack/reply/task/defer), **черновик ответа** (если needs_reply).
- Пользователь в Cursor: правки черновиков, «отправить» (если Slack MCP умеет отправку — тогда следующий шаг), «создать задачу», «пропустить».
- Никакой авто-отправки без явного подтверждения (безопасность и тон).

### Обновление vault

- **Person page:** при обработке сообщений от известных персон — секция «Recent Slack» (аналог Recent Emails) со ссылкой на канал/тред и кратким контекстом.
- **Задачи:** созданные через Work MCP сразу линкуются к персонам и при желании к проектам.

## «Отвечать как я» — где хранить и как использовать

- **Глобально:** `System/user-profile.yaml` — communication (formality, directness). Уже используется для тона в Dex.
- **На персону:** «Working Style Notes» в person page — как они любят общаться; это подсказывает и тон ответа (более формально/коротко/развёрнуто).
- **MVP черновиков:** без отдельного «голоса» — просто короткие, по делу, без запрещённых фраз. Позже можно добавить:
  - `06-Resources/Dex_System/slack-reply-style.md` — примеры типовых ответов (ack, делегирование, «вернусь позже»);
  - или блок в person page: «Как я обычно отвечаю этому человеку» (если пользователь начнёт править черновики — можно сохранять примеры в learnings и потом выносить в стиль).

## Реализация по шагам

1. **Slack MCP:** добавить в конфиг, OAuth, проверить: список чатов, чтение истории каналов/DM за период (или непрочитанные). Уточнить по доке Slack MCP, есть ли «unread» или только «messages in channel since X».
2. **Скилл `/slack-digest` (или `/slack-process`):**
   - аргументы: период (today / last 4h / since HH:MM) или «unread»;
   - шаги: загрузка Week Priorities + pillars, индекс персон/проектов (как в triage), запрос к Slack MCP, для каждого сообщения — классификация, действие, при needs_reply — черновик с учётом person context;
   - вывод: Markdown-отчёт с рекомендациями и черновиками.
3. **Конфиг (опционально):** `System/slack-digest.yaml` — каналы/DM для включения, окно по умолчанию, исключения (каналы только FYI).
4. **Отправка (фаза 2):** если Slack MCP поддерживает отправку — кнопка/команда «отправить этот черновик» с явным подтверждением.
5. **Обновление персон:** при обработке — дописывать в person page блок Recent Slack (дата, канал, одна строка контекста).

## Отличие от «просто процессов»

Процессы и митинги уменьшают количество входящих и снимают часть вопросов. Но пока их нет или их недостаточно, PKM даёт:

- **Единое место контекста:** кто этот человек, что у нас с ним открыто, что в приоритетах на неделю — уже в vault, не в голове.
- **Батч вместо постоянного переключения:** один запуск скилла заменяет «каждый раз открывать тред и вспоминать».
- **Черновики в твоём стиле:** не универсальный бот, а ответы, сгенерированные с учётом твоего профиля и стиля общения с конкретным человеком.

Итог: use case обрабатывается в Dex как **новый скилл поверх Slack MCP**, с тем же контекстом из vault, что и в email-process и triage, с фокусом на триаж и предложенные ответы (MVP без авто-отправки).
