**Вердикт:** Проверил код интеграции cursor-team-kit в Dex — то, что мы только что добавили. Slash работает правильно: короткая запись в меню отправляет агента читать полную инструкцию из библиотеки, а не выдумывать. Пользоваться можно. Но ревью считает интеграцию **недожатой для долгой жизни**: через несколько обновлений с GitHub описания в slash и реальные тексты skills **разъедутся**, а скрипт синхронизации slash **снова раздуется** копипастой, если добавить ещё одну библиотеку.

**Действия**
1. Пока не правишь код — просто пользуйся slash, они уже рабочие.
2. Если будешь обновлять skills с upstream — помни: одного скрипта обновления библиотеки мало, stub в меню Cursor сами не подтянут новые описания.
3. Если скажешь «делай фикс» — добавлю автогенерацию stub и упрощу поиск канонического файла в скрипте синхронизации slash.

**Детали — что именно нашло ревью**

**Проблема 1 — два источника правды для slash.**  
Есть скрипт, который умеет создавать тонкие обёртки автоматически. Для 18 skills team-kit обёртки написаны руками. Скрипт обновления библиотеки с GitHub меняет только тексты в `Skills_library/cursor-team-kit/skills/`, а строки в `.cursor/skills/*/SKILL.md` остаются старыми. Итог: в меню `/` одно описание, в файле другое.

**Проблема 2 — скрипт ищет канонический skill цепочкой «если папка A, иначе B, иначе C».**  
Сейчас там уже три библиотеки подряд. Следующая — ещё один блок кода вручную. Это не ломает работу сегодня, но типичный рост «спагетти в скрипте».

**Что нормально**
- Скрипт `Skills_library/cursor-team-kit/update.sh` короткий и понятный: клонирует только нужную папку с GitHub и кладёт в библиотеку.
- Разделение «полный текст в Skills_library, stub только для меню» — правильная архитектура для Dex.
- Ни один наш файл не раздут за тысячу строк.

**Мелочь для людей:** slash `weekly-review` (team kit) легко перепутать с `week-review` (Dex) — разные skills, похожие имена.

**Итог ревью:** не «всё плохо», а «работает, но два технических долга стоит закрыть до следующего обновления с GitHub».
